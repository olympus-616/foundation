The Ultimate “Backend” for Salesforce Hosted Apps

We finally got through the global callable refactor this week. I am ready to revisit the security review process. It took almost a year longer to get it the way I wanted it… but good things take time and I’ve got a lot of mouths to feed.

Anyway, here are the features that will make up the backend app layer (for Salesforce hosted applications if you are new to my blog)

IPlugin — this sits at the base of the architecture… allowing dynamic instantiation AND modularization of all of the rest of the components of the system. This module is where you register your interfaces and dynamic code. It makes the entire architecture loosely coupled and I’m so excited to show how this is going to make future upgrades and add-ons SOOOO easy to work with.

IConfig — this is a configuration store to hold any and all configuration data both from within our Reactforce Suite of apps as well as any client specific configuration that maybe required. This makes it extremely easy to deploy, manage, and use configuration data of numerous data types. It also supports encryption of configuration data allowing you a super simple and auditable way to keep secrets like API keys TRULY encrypted at rest.

ICustomExc — this is a wrapper on custom exceptions that makes it super easy to throw, catch, and log all the important things you care about when dealing with Apex exceptions. For example all of the contents of the call stack will be written to an SObject via the ILogger. (And yes they survive DML rollbacks thank you platform events I love you).

IDb — this is a database utility for handling most of the DML in the system. It handles unit of work style caching of datasets, or you can commit each transaction. It makes it very easy to work with and without sharing, and handles all of the magic necessary to get your app safely through security review. (Assuming this app passes security review of course!!)

ISoql — this is another utility for handling many of your SOQL needs. It will very easily return maps of data with any object/field that you have security access too. While it doesn’t handle complex queries it handles most of my use cases and makes the code super simple to write and maintain.

IObjectTrigger- Everyone else has a trigger handler… why can’t I throw another in the mix! This trigger solution has built in on/off. It also supports pending trigger updates (if you have unrelated database activity that can wait until the end of the first trigger fire… allowing less unnecessary recursion through the environment. But at the end of the day… a trigger is a trigger.

IPlatformEvent- This framework uses a generic event type to allow super simple creation and handling of platform events via custom handlers (which can be apex or flow). Just register a new event type with IPlugin, write your corresponding handler and you are off and running. All events can be logged and there is also a dead-letter queue that supports retrys.

ILogger- Ive been dreaming of this app ever since I started on Salesforce.com 15 years ago. As an ex-Java developer I had a man-crush on log4j and I just have hated every minute of debugging issues on Salesforce. ESPECIALLY on production managed packages where logging is obfuscated without a lot of fuss. Well not anymore… I finally have the logging solution I wanted as a Developer, Architect, AND CTO. Logging is now as easy as an on/off switch. And logs are automatically pruned based upon your own retention policies.

IApi- This is probably my favorite feature on the backend. It makes Salesforce feel and act like an Express.JS backend vs a tangled and unorganized collection of 1000s of pieces of metadata as most large organizations evolve to. The apis are similar in nature to a typical services layer. However every function is written RESTful style (GET/POST/PATCH/PUT/DELETE) and makes organizing your business logic EXTREMELY easy. The API layer can be accessed internally from Salesforce via Apex/Flow/LWC/Visualforce and externally (HTTP/Postman/etc) via an awesome route based system that supports dynamic paths, variables, etc. There is even route based security on this solution. Adding routes and handlers is so simple that basically everyone is going to end up being a front-end developer as this is like the one-controller-to-rule-them-all. This code is all you need to design, code, and manage an enterprise API solution (sorry to the Mulesoft lovers out there). This code is so awesome that I broke up with log4j and just learned self-love of my own solutions :)

IAsync- This plugin makes working with Async salesforce about as easy as it can be. Each type of job (@future, Queueable, Batch, Scheduled) is now defined as an AsyncWorker, all of which gain similar cross-cutting concerns such as scheduling, ad-hoc execution, pausing, error handling, and of course… LOGGING! After writing thousands of batch jobs in my life I have everything I need and want to make writing these as painless as possible. The scheduling solution supports CRON expression but even lets you define your scheduled jobs in human terms such as “Run Every Hour” which will dynamically create and maintain the CRON expressions for you. There is even a scheduling console that every Salesforce admin will absolutely love. (Pause/Unpause anyone?)

First things first — CI/CD

As part of my “Let’s Build a Salesforce App Together” series…

I am not a devops expert. I am however a self proclaimed expert in building serverless systems (Salesforce, AWS, React, Netlify, etc) and my latest passion is end to end CI/CD.

This is not easy to get going, and usually is an after thought for most teams I have ever worked with. But for me, in my navy seal approach to system building, it is one of the MOST important pieces of the system.

For every app I build, the very FIRST thing I work on is the CI/CD process. Functional development does not even begin until there is a deployment pipeline and process for EVERY component of the system.

In order to build systems fast and build cheap, building automated depoyment pipelines must be done. Otherwise each migration of the system from environment to environment will be error prone or unpredictable. Without an automation pipeline more time will be spent on migration and environment management than actual functional development. This is one of my main pieces of advice for anyone wanting to build an app or a startup company.

For those of you in a corporate environment, do whatever you can to bring in the right tools and processes for automated deployment processes as early in the project as possible. This is a key differentiator for my career in building zero error deployments and delivering new systems to market in record time.

So what makes a good deployment pipeline? Each project is so different… different components, platforms, programming languages, team sizes, deployment dependecies… the list goes on and on. Software is hard. But for every successful project that I have delivered there have been similar architectural principles. Here is a list of what I think are the MOST important.

  1. Source control management — meaning each component of the system is tracked through source control (Github is my personal favorite) and each environment should have a representation in the source control system. I use branches such as “uat” or “staging” and “prod” to keep each environment in alignment with its respective branch.
  2. Multiple Environments fit for purpose — meaning have enough environments that you need, and no more than you need. On a simple component, this maybe as low as 2 different environments. On a complex component, there maybe dozens if not hundreds of environments (and automating dozens or hundreds of environments is critical).
  3. Ability to easily and consistently build a developer environment — this means workstation setup instructions, tools, procedures, and instructions to get up and running fast. This is critical I promise. I use my own instructions for myself over time as I bounce from one area of the system to another.
  4. Developer environment isolation — this means each developer has their own environment and each change is isolated to a developer environment and source code feature branch.
  5. Developer environment integration — this means each development environment is fully functional in capability. I can’t stress this one enough. There must be enough data and real or mock endpoints to ensure the development environment is representative of production and NOT a sub-set of functionality.
  6. Ability to easily and consistently migrate a feature into a new environment — each developer added to the project adds in increasing complexity in the deployments. While migration for a single feature of a single component to the UAT environment maybe easy… tracking each developers change throughout each environment quickly becomes unwieldy and will require LOTS of meetings or LOTS of resources spent on deployments as opposed to building cool new features.
  7. Ability to easily identify what features exist in which environment — this means either maintaining a very strict source control flow and/or a ticketing system that is kept to date with the feature branches. The faster you build, the more difficult this becomes unless there is a robust process backing it up.
  8. Ability to “hold” or “gate” features in a development environment until the right time — Each development environment MUST be kept in sync with the appropriate upstream environment or you risk overwriting work as you migrate features into the next environment. If a feature is NOT ready for deployment, it should be able to be easily mothballed into a feature branch indefinitely. The feature branches should be kept in sync with the main branch (manually or automatically if possible).
  9. A release train — there should be a gate between development and acceptance and deployment. Once a feature is accepted, the feature is migrated onto the release train which means that it is headed to production in the next production release. If a feature is accepted but NOT ready for deployment, it cannot and should not be added to the release train environment.
  10. Ability to “roll back” the code and configuration to an earlier state — this is easier said than done and depending on the platform type there maybe a number of manual configuration steps that are introduced during deployment windows. For me this is more of an art than a science and my priority is to ensure that each stable release is tagged in the source control system which could then be “easily” re-deployed if necessary.
  11. Tools, processes, and documentation that support the process from beginning to end — maybe I’m just getting old but I find myself reading my own documentation more and more. Trust me… your future self will REALLY appreciate your effort to document your development and deployment processes.

Mind you this list can be significantly more complicated, but the above list should be considered minimum requirements for a deployment pipeline. I’m sure you may have more… leave a comment and I will update the list (if I agree of course!)

Over the life of this blog I will dig into these subjects… but for now I want to get into the actual apps that I’m building. This explains why the first requirements for the new system are building the entire system ci/cd pipeline (for which I will need at least 3 separately operating pipelines).

So first up… CI/CD of my SFDX plugin delivered through NPM.

Next up… CI/CD of my Salesforce reusable utility library delivered through the AppExchange and through GitHub using CumulusCI.

After that… CI/CD of my Salesforce app that will use BOTH the plugin and the reusable library as dependencies.

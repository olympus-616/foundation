The particular feature, which I will quickly summarize:

We just finished upgrading our Platform Event Manager library. So what is that? Think of it like what fedex does for your important deliveries, Platform Event Manager does this for your async communication.

It takes the ease and learning curve of Salesforce and it adds AWS SQS type concepts to be your one stop shop for all of your queue requirements.

It’s the whole “one platform event to rule them all” feature that I wrote about some time ago. Finally done. Finally perfected.

I finally finished what every good Salesforce architect has always wanted (and most likely never had)

We built FedEx for platform events.

  • Create any generic json payload into a dynamic event. Simply define the event type and the related apex or flow handler. Basically just serialize some data, write in an envelope where you want it to go, and let FedEx take it from there. We even create a tracking number if you want it.
  • Define an event policy which specifies things like: should the event be posted immediately, or wait for a successful database commit? If the event fails, how many times should it be automatically retried? (Yes… you heard me… automatic retry)
  • Create and post the event from flow, apex, lwc, or really anywhere.
  • Choose whether to log your platform event activity to a persistent log for troubleshooting. Log both the publishing event as well as the consumer side for full traceability.
  • Capture the individually failed events in a Platform Event Dead Letter Queue (DLQ) for monitoring, alerting, manually reprocessing the event, or automatically retrying up to the number of times as defined in the policy.
  • Use our API manager to create a platform event a simple POST request away. (Now your front end apps can 100% manage the apps async requirements if necessary)
  • Defer your messages to be processed at a later time. You can drop a message in a queue for a specific date/time and let the DLQ and auto-retry logic manage the messages at a later time. Think of it like Time Based Workflow… but one that makes sense and is easy to debug and modify given everything runs off of SObjects. Using this technique you can automatically “schedule” anything in the system by sending a very simple message.
  • And the latest feature, maybe even cooler than auto retries… platform events now integrates directly with our advanced queuing/state management machine (as part of the BPM plugins) What this means is that you can build a complex state machine to manage long-running, async processes. Until now doing something like this in Salesforce has been so complicated to do this without building complex dependencies across the system architecture. It’s like a FedEx delivery system that will not only make sure your package gets there, but they will make sure that the package is signed, sealed, and delivered. And then the FedEx driver goes away and you never have to think about it again. Guaranteed delivery.
  • Also on the roadmap… automatic encryption of the event contents so that only the correct consumer can decrypt the message.

Basically it’s all I could ever think about having to help me quickly build and then effectively manage a large decoupled, event driven system at scale. These systems are usually too complex due to their decoupled, async nature. It’s hard to keep things from falling in between the cracks. Therefore usually we end up having to build tightly coupled systems with lots of synchronous and near real time error handling so that humans can manage a lot of the errors. This is extremely inefficient and extremely expensive in terms of human capital.
